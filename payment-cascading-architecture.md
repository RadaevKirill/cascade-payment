# Архитектура системы каскадирования платежей

## 1. Цель и область решения

Система обеспечивает создание платежа по заказу и выбор подходящего платёжного провайдера. Если попытка завершилась отказом, система классифицирует его и выбирает дальнейшее действие: прекращает обработку, предлагает клиенту исправить данные или, когда это допустимо, обращается к следующему провайдеру из разрешённого маршрута. Результаты попыток сохраняются и доступны для анализа.

В основе решения — **модульный монолит** на Python и FastAPI. Платёжная логика выделена в самостоятельный модуль с явными интерфейсами, что позволяет в дальнейшем вынести её в отдельный сервис.

### Допущения

- Для заказа создаётся один логический платёж на полную сумму; он может включать несколько последовательных попыток у провайдеров.
- Клиент заранее выбирает способ оплаты. Маршрут включает только совместимых провайдеров с учётом метода, валюты и доступности.
- Сумма и валюта берутся из заказа на стороне сервера.
- В примере используются два независимых тестовых провайдера. NOWPayments рассматривается как возможный адаптер для криптовалютных платежей; он не подменяет карточный способ оплаты.
- Возвраты, выплаты и политика обработки частичных и поздних оплат требуют отдельного согласования. Такие случаи фиксируются и направляются на разбор.

**Принцип безопасности каскада:** новая попытка создаётся только после подтверждения, что предыдущая не может привести к оплате, и только если это разрешено правилами для конкретной причины отказа. Если результат обращения неизвестен, каскад приостанавливается до сверки.

└──────────┘               │                                       │

**Рисунок 1.** В PostgreSQL хранятся состояния платежей и события для фоновой обработки. Пунктирная по смыслу связь через outbox означает публикацию задач в Redis отдельным процессом, а не прямую запись PostgreSQL в Redis.

### Границы модулей

| Модуль | Ответственность |
|---|---|
| **Payments** | Платежи и попытки, выбор маршрута, взаимодействие с провайдерами, webhook и сверка |
| **Orders** | Заказы, сумма и валюта; получение результата оплаты через публичный интерфейс или событие |
| **Identity** | Аутентификация по JWT и проверка прав доступа |
| **Notifications** | Асинхронные уведомления, в том числе через Telegram |
| **Files** | Хранение файлов и отчётов в S3-совместимом хранилище |
| **Integrations** | Адаптеры внешних API, включая Google и RunPod, если они нужны другим бизнес-сценариям |

Google, RunPod, Telegram и S3 не участвуют в принятии решения об успешности платежа. Их доступность не должна блокировать обработку платежа.

### Внутреннее устройство Payments

Модуль следует принципам DDD и Clean Architecture:

- **Domain:** сущности `Payment` и `PaymentAttempt`, денежные значения, правила переходов состояний. Сущности представлены Pydantic-моделями.
- **Application:** сценарии создания платежа, выбора следующего провайдера, обработки webhook и сверки; интерфейсы репозиториев и провайдеров.
- **Infrastructure:** SQLAlchemy-репозитории, адаптеры платёжных API на httpx и задачи Taskiq.
- **Presentation:** маршруты FastAPI и схемы запросов и ответов.

Зависимости направлены от инфраструктуры к прикладному и доменному слоям. Доменные модели отделены от ORM-моделей и не зависят от HTTP, базы данных или очереди.

## 3. Сценарий каскадирования

```text
Клиент          API / Payments       Провайдер A       Провайдер B
  │                    │                   │                  │
  │ Создать платёж     │                   │                  │
  │ + ключ повтора     │                   │                  │
  ├───────────────────►│                   │                  │
  │                    │ Сохранить платёж  │                  │
  │                    │ и попытку A       │                  │
  │                    ├──────────────────►│                  │
  │                    │ Мягкий отказ      │                  │
  │                    │◄──────────────────┤                  │
  │                    │ Сохранить отказ   │                  │
  │                    │ и попытку B       │                  │
  │                    ├─────────────────────────────────────►│
  │                    │ Реквизиты оплаты                     │
  │                    │◄─────────────────────────────────────┤
  │ Статус и реквизиты │                   │                  │
  │◄───────────────────┤                   │                  │
  │                                                           │
  │ Оплата у провайдера B                                      │
  ├──────────────────────────────────────────────────────────►│
  │                    │ Webhook о результате                 │
  │                    │◄─────────────────────────────────────┤
  │                    │ Проверить, сохранить и обработать    │
  │ Получить статус    │                   │                  │
  ├───────────────────►│                   │                  │
  │ Успешно оплачен    │                   │                  │
  │◄───────────────────┤                   │                  │
```

**Рисунок 2.** Основной сценарий: переход к провайдеру B допустим после мягкого отказа A, если политика разрешает переход и прежняя операция не может привести к оплате. Если ответ A потерян или его результат неизвестен, переход к B не выполняется: сначала запускается сверка.

1. API проверяет JWT, права на заказ и ключ идемпотентности. Создаёт платёж и возвращает его идентификатор.
2. Фоновая задача выбирает подходящих провайдеров по действующим правилам и сохраняет первую попытку.
3. Система фиксирует намерение отправить запрос и обращается к провайдеру. Сетевой вызов не удерживает транзакцию БД открытой.
4. При однозначном отказе система сохраняет его код и классификацию. Для мягкого отказа применяется настроенная политика повтора или перехода; при жёстком отказе автоматический каскад прекращается. Перед новой попыткой необходимо подтвердить отсутствие действующей операции.
5. При успешном создании операции сохраняются её идентификатор и реквизиты. Клиент получает их и выполняет оплату.
6. Результат поступает через webhook или уточняется при сверке. После подтверждения система обновляет платёж и уведомляет модуль заказов.
7. Если подходящие провайдеры закончились, платёж завершается с ошибкой. При неизвестном результате работа приостанавливается для сверки.

После выдачи клиенту действующих реквизитов новая попытка не создаётся, пока не установлено, что прежняя операция больше не может быть оплачена. Для криптоплатежей отдельно требуется определить обработку переводов, поступивших после истечения срока.

### Классификация отказов

Адаптер провайдера переводит его исходные коды в внутреннюю классификацию, сохраняя оригинальный код и сообщение для аудита. Классификация зависит от договора и документации конкретного провайдера и платёжного метода; одинаковые HTTP-коды сами по себе не означают одинаковую причину отказа.

| Категория | Примеры | Действие |
|---|---|---|
| **Жёсткий отказ** (`HARD_DECLINE`) | Недействительные платёжные данные, запрещённая операция, окончательный отказ эмитента или требование не повторять операцию | Остановить автоматический каскад. Предложить исправить данные или выбрать другой способ оплаты согласно бизнес-правилам. Обходить запрет сменой провайдера нельзя. |
| **Мягкий отказ** (`SOFT_DECLINE`) | Временная недоступность провайдера или временный отказ, явно допускающий повтор, если исход операции подтверждён | По правилам конкретного кода выполнить ограниченный повтор с задержкой либо перейти к другому совместимому провайдеру. Новая попытка допустима только при подтверждении, что предыдущая не приведёт к оплате. |
| **Требуется действие клиента** (`ACTION_REQUIRED`) | Дополнительная аутентификация или подтверждение, если это предусмотрено методом оплаты | Вернуть клиенту требуемое действие и дождаться результата; не обходить его автоматическим каскадом. |
| **Неизвестный результат** (`UNKNOWN`) | Таймаут или разрыв связи после возможной отправки запроса | Остановить повторы и переход к другому провайдеру; запустить сверку. Это состояние не приравнивается к мягкому отказу. |

Недостаточно средств, антифрод-отказы и прочие неоднозначные причины нельзя универсально отнести к одной категории: действие определяется правилами провайдера, платёжной системы и продукта. Неизвестный или неподдерживаемый код обрабатывается консервативно: автоматический переход отключён до уточнения. Для мягких отказов задаются максимальное число попыток, задержка, применимость к провайдерам и правила защиты от циклов. Технические ошибки, при которых точно подтверждено, что запрос не был отправлен или операция не создана, могут допускать повтор; одна лишь ошибка сети этого не доказывает.

Например, временный отказ провайдера A, который подтверждает отсутствие созданной операции и разрешает повтор, может привести к попытке у провайдера B. Окончательный отказ эмитента о запрещённой операции завершает автоматический каскад. Для NOWPayments и тестовых провайдеров конкретное соответствие кодов этой классификации определяется при интеграции; примеры отказов эмитента относятся к карточным провайдерам, а не предполагаются для криптоплатежей.

## 4. Данные и состояния

| Сущность | Ключевые данные | Назначение |
|---|---|---|
| `Payment` | ID, заказ, клиент, сумма, валюта, метод, статус, ключ идемпотентности | Логическое намерение оплатить заказ |
| `PaymentAttempt` | ID, платёж, провайдер, номер попытки, внешняя ссылка и ID, статус, реквизиты, категория и исходный код отказа | История взаимодействия с одним провайдером |
| `ProviderRoute` | Способ оплаты, валюта, приоритет, доступность, версия правил | Выбор и порядок подходящих провайдеров |
| `WebhookEvent` | Провайдер, идентификатор или отпечаток события, полезная нагрузка, состояние обработки | Надёжная обработка и дедупликация уведомлений |
| `OutboxEvent` | Тип события, ссылка на объект, данные, состояние публикации | Передача событий в очередь после изменения данных |

Денежные суммы хранятся в PostgreSQL как `NUMERIC`, в Python используются `Decimal`. Ссылки на провайдера и история смены состояний сохраняются для сверки и аудита.

**Основные состояния платежа:** `CREATED`, `PROCESSING`, `AWAITING_PAYMENT`, `SUCCEEDED`, `FAILED`, `EXPIRED`, `REVIEW_REQUIRED`.

**Основные состояния попытки:** `CREATED`, `SUBMITTING`, `AWAITING_PAYMENT`, `SUCCEEDED`, `DECLINED`, `FAILED`, `EXPIRED`, `UNKNOWN`, `REVIEW_REQUIRED`.

Переходы проверяются доменной логикой. `DECLINED` обозначает однозначный отказ; `UNKNOWN` — неопределённый результат, требующий сверки. Частичная или поздняя оплата, а также противоречивые данные приводят к `REVIEW_REQUIRED` в ожидании согласованной бизнес-политики. Повторный или запоздавший webhook не должен автоматически отменять уже подтверждённый результат.

## 5. Надёжность и обработка сбоев

| Ситуация | Поведение системы |
|---|---|
| Клиент повторил запрос | Ключ идемпотентности в рамках клиента возвращает существующий платёж; повтор с иными параметрами даёт конфликт |
| Одновременные операции над платежом | Транзакции и ограничения PostgreSQL обеспечивают согласованность и не допускают несколько активных попыток |
| Провайдер вернул однозначный отказ | Сохраняются исходный код и категория; жёсткий отказ останавливает каскад, для мягкого применяется ограниченная политика повтора или перехода |
| Таймаут или потерян ответ провайдера | Попытка считается неопределённой; новая не создаётся до выяснения результата |
| Приложение упало после отправки запроса | Незавершённая попытка обнаруживается фоновой сверкой. Если найти её у провайдера невозможно, требуется ручной разбор |
| Webhook доставлен повторно или не по порядку | Событие дедуплицируется, переход проверяется; повторная обработка не создаёт повторный бизнес-эффект |
| Webhook не пришёл | Фоновая задача запрашивает состояние у провайдера, если его API позволяет это сделать |
| Redis или воркер недоступен | Данные и события остаются в PostgreSQL; доставка и обработка возобновляются после восстановления |

Надёжная передача фоновых событий строится через **transactional outbox**: изменение состояния и запись события выполняются в одной транзакции PostgreSQL. Отдельный процесс публикует события в Taskiq через Redis. Публикация и доставка могут повторяться, поэтому обработчики идемпотентны. Для очереди предлагается Taskiq Redis Streams с подтверждением сообщений; восстановление и настройки необходимо проверить на выбранных версиях и в интеграционных тестах.

Система не предполагает, что собственный `order_id` автоматически делает запрос к провайдеру идемпотентным. Повтор создания допустим только при документированной гарантии провайдера. Без возможности надёжного поиска или безопасного повтора неопределённая попытка остаётся на ручной сверке.

## 6. API и безопасность

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/payments` | Создать платёж по заказу; принять `Idempotency-Key` |
| `GET /api/v1/payments/{id}` | Получить статус и, когда доступны, реквизиты оплаты |
| `GET /api/v1/payments/{id}/attempts` | Получить историю попыток при наличии соответствующих прав |
| `POST /api/v1/webhooks/nowpayments` | Принять уведомление NOWPayments |
| `GET /health/live`, `GET /health/ready` | Проверить работоспособность процесса и готовность принимать трафик |

Создание платежа может возвращать `202 Accepted` и ID: подготовка реквизитов выполняется асинхронно. Доступ к платёжным данным ограничивается владельцем заказа и уполномоченными операторами. JWT проверяется по подписи, сроку действия, издателю, аудитории и правам.

Webhook использует отдельную проверку подлинности, а не пользовательский JWT. Для NOWPayments проверяется подпись IPN по актуальным правилам провайдера; затем событие сохраняется в БД и быстро подтверждается. До изменения статуса дополнительно проверяются связь с попыткой, идентификаторы, сумма и валюта. Если событие не удалось надёжно сохранить, возвращается ошибка, позволяющая провайдеру повторить доставку.

Секреты хранятся вне репозитория; чувствительные данные и ключи исключаются из логов. Используются HTTPS, контролируемые таймауты и ограничения частоты запросов. Для анализа работы ведутся структурированные логи, аудит действий, метрики успеха провайдеров, зависших попыток и возраста событий outbox.

| httpx | Асинхронные вызовы внешних API и адаптеров провайдеров |

| S3, aioboto3 | Хранение файлов и отчётов при необходимости |

## 8. Проверка решения и дальнейшее развитие

Ключевые сценарии проверки первой версии:

1. Первый провайдер возвращает мягкий отказ, разрешающий переход, второй создаёт платёж; история содержит обе попытки. При жёстком отказе вызова второго провайдера нет.
2. Провайдер не ответил: следующая попытка не создаётся до сверки.
3. Повторные и параллельные запросы с одним ключом не создают дублирующий платёж; несовпадение параметров вызывает конфликт.
4. Повторный webhook и повторная доставка задачи не приводят к повторному изменению бизнес-состояния.
5. После падения процесса между вызовом провайдера и сохранением ответа попытка обнаруживается для сверки.
6. Некорректная подпись webhook отклоняется; поздняя или частичная оплата направляется на разбор.

Для демонстрации достаточно двух тестовых провайдеров с управляемыми ответами. Реальная интеграция с NOWPayments требует проверки возможностей конкретного API и аккаунта, включая тестовую среду, идентификацию платежей, статусы и подпись IPN.

При последующем выделении Payments в микросервис его публичные команды и события станут внешними контрактами. Модулю потребуется собственное владение данными, версионирование контрактов и межсервисная доставка событий; перенос нельзя считать автоматическим только благодаря структуре каталогов.
