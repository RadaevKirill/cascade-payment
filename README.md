# Payment cascading

Небольшой демонстрационный API каскадирования платежей на FastAPI и SQLite. Два встроенных имитатора используют ссылки-заглушки `example.com`; отдельно доступен Stripe Checkout в тестовом режиме. Сумма и валюта берутся из тестового каталога заказов на сервере.

## Запуск

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/). В каталоге проекта:

```bash
uv sync --group dev
uv run uvicorn main:app --reload
```

Документация API доступна по адресу http://127.0.0.1:8000/docs. База `payments.db` создаётся при запуске; путь можно изменить переменной `DATABASE_PATH`.

## Stripe Checkout: полный тестовый платёж

1. Создайте аккаунт Stripe и получите секретный ключ **test mode** в [Dashboard](https://dashboard.stripe.com/test/apikeys). Приложение принимает только ключи с префиксом `sk_test_`. Не передавайте секретные ключи в чат и не добавляйте их в репозиторий.
2. Установите и авторизуйте [Stripe CLI](https://docs.stripe.com/stripe-cli), затем запустите в отдельном терминале:

   ```bash
   stripe listen --forward-to localhost:8000/api/v1/webhooks/stripe
   ```

   Команда выведет секрет подписи `whsec_...`. Оставьте её работающей: она доставляет события на локальный сервер.
3. В другом терминале задайте переменные окружения и запустите сервер:

   ```bash
   export STRIPE_SECRET_KEY='sk_test_...'
   export STRIPE_WEBHOOK_SECRET='whsec_...'
   uv run uvicorn main:app --reload
   ```

   При необходимости задайте `PUBLIC_BASE_URL` — адрес приложения, на который Stripe вернёт браузер после оплаты; по умолчанию `http://localhost:8000`.
4. Создайте сессию:

   ```bash
   curl -X POST http://127.0.0.1:8000/api/v1/payments/stripe \
     -H 'Content-Type: application/json' -H 'Idempotency-Key: stripe-order-1' \
     -d '{"order_id":"order-1"}'
   ```

   Откройте `payment_url` из ответа и оплатите на странице Stripe тестовой картой `4242 4242 4242 4242`, указав любую будущую дату и любой трёхзначный CVC. См. [тестовые карты Stripe](https://docs.stripe.com/testing). Возврат браузера сам по себе не подтверждает оплату: после получения подписанного webhook статус можно проверить через `GET /api/v1/payments/{id}`.

Stripe работает отдельным маршрутом от имитаторов, поэтому при ошибке Stripe автоматический переход к другому провайдеру не выполняется. Неопределённый результат создания сессии получает статус `REVIEW_REQUIRED`; автоматической сверки пока нет. Для нового прогона используйте другой тестовый заказ либо удалите локальную базу после остановки приложения.

## Пример с имитаторами

```bash
curl -X POST http://127.0.0.1:8000/api/v1/payments \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: example-1' \
  -d '{"order_id":"order-1"}'
```

По умолчанию провайдер A возвращает мягкий отказ, а B создаёт тестовые реквизиты. Заказы: `order-1` — 100 USD, `order-2` — 49.90 EUR, `order-3` — 250 USD. Поля `provider_a` и `provider_b` позволяют выбрать ответ каждого провайдера: `success`, `soft_decline`, `hard_decline`, `unknown`, `action_required`. Мягкий отказ запускает следующую попытку, жёсткий завершает платёж, неизвестный результат отправляет его на разбор, а требование действия клиента останавливает каскад. Повтор запроса с тем же ключом и параметрами возвращает тот же платёж; для каждого заказа разрешён один платёж.

Получить результат и историю: `GET /api/v1/payments/{id}` и `GET /api/v1/payments/{id}/attempts`. Чтобы имитировать результат оплаты, отправьте `POST /api/v1/webhooks/test` с заголовком `X-Test-Secret: demo-secret` и телом:

```json
{"event_id":"event-1", "attempt_id":"ID попытки", "status":"succeeded", "amount":"100.00", "currency":"USD"}
```

Допустим также статус `failed`. Секрет задаётся переменной `TEST_WEBHOOK_SECRET`. Повтор события с тем же ID и содержимым не меняет результат; противоречивый результат отправляет платёж на разбор.

```bash
uv run pytest
```

## Ограничения

Это локальный прототип, не платёжная система для эксплуатации: нет JWT и разграничения доступа, фоновой сверки, очередей, миграций и интеграции с заказами. Stripe подключён только в тестовом режиме; его webhook проверяет подпись. Каскад выполняется внутри HTTP-запроса; SQLite и секрет по умолчанию подходят только для демонстрации. Состояние `REVIEW_REQUIRED` разрешается вручную вне этого прототипа. Архитектура дальнейшего развития описана в `payment-cascading-architecture.md`.
